## Why the int_ layer exists

`int_encounters_enriched` and `int_readmissions` are deliberate intermediate
models — they handle two responsibilities that don't belong in staging
(transform-heavy: LAG window for readmission detection, season derivation)
or in marts (output-shaped):

- **Encounter enrichment**: age_group, season, is_emergency derivation
- **Readmission detection**: per-patient LAG window over admission_date,
  previous_admission_count, is_readmission flag

Both feed `fact_patient_encounters` so the fact table stays clean SELECT.

## When this DAG changes

```
ADD A NEW DIMENSION         →  marts/core/dim_<name>.sql
ADD A NEW MEASURE           →  int_encounters_enriched.sql (compute) +
                                  fact_patient_encounters.sql (surface)
ADD AN AUDIT COLUMN         →  sources.yml + stg_healthcare.sql passthrough
                                  + fact_patient_encounters.sql (if surfaceable)
CHANGE THE READMISSION RULE →  int_readmissions.sql + assert_valid_readmission_logic.sql
```

Each change = one PR, regression-gated by the existing dbt tests +
`scripts/checkpoint.py` data-quality gate.

## Lineage observability roadmap

```
NOW (Phase A — committed)        what's visible today
   ✅ structural lineage          via dbt DAG (this file)
   ✅ test pass/fail per model     via dbt tests + CI
   ✅ row count per model          via dbt run-results

NEXT (Phase B — queued)          what's deferred
   ⌛ column-level lineage         via dbt-labs/dbt-osmosis OR Datafold
   ⌛ upstream/downstream impact   via dbt-labs/dbt-checkpoint
   ⌛ freshness SLA monitoring     via Soda OR Monte Carlo

REAL (Phase D — only when warranted)
   ❌ enterprise data catalog       (DataHub / Atlan / Collibra)
   ❌ automated drift webhooks      (Great Expectations runtime hooks)
```
